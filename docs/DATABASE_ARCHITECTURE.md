# DATABASE_ARCHITECTURE.md

Implemented database architecture for the Fashion ERP Backend, established in Phase 03.

This document describes what is actually implemented. Business schema (products,
sales, inventory, etc.) does not exist yet and is not described here — see
`‌ai/Phase 03.md` onward for the roadmap.

## Technology

- MySQL 8.0.40 (Docker, Phase 02)
- TypeORM 0.3.x
- InnoDB storage engine
- `utf8mb4` / `utf8mb4_unicode_ci` character set and collation

## Primary Key Strategy

UUID v4, generated by MySQL (`@PrimaryGeneratedColumn('uuid')`), stored as
`CHAR(36)`. Chosen over `BINARY(16)` for simplicity, native TypeORM support, and
readability during development; storage/index overhead is acceptable at this
project's expected scale. Business identifiers must never be sequential
auto-increment integers.

## Timestamp Strategy

All entities extending `BaseEntity` (`src/database/base.entity.ts`) get:

- `created_at` (`TIMESTAMP`, set on insert)
- `updated_at` (`TIMESTAMP`, set on insert and update)
- `deleted_at` (`TIMESTAMP`, nullable — soft delete marker)

Timestamps are stored as MySQL `TIMESTAMP` values. Business-date/timezone
philosophy beyond this foundation is deferred to the phases that introduce
business dates (sales, accounting, etc.).

## Soft Delete Strategy

`BaseEntity` includes `deletedAt`, making TypeORM's `softRemove()` /
`restore()` / `withDeleted()` available to any entity that extends it. Whether
a given future entity actually uses soft delete is decided per-entity when
that entity is created — not every table automatically gets soft delete.
Append-only/ledger-style data (future inventory ledger, accounting entries,
payments) must use reversal/cancellation patterns instead of soft delete, per
`‌ai/Phase 03.md` §32-33.

## Naming Conventions

- Tables: plural, `snake_case` (e.g. `users`)
- Columns: `snake_case` (e.g. `created_at`, `password_hash`)
- Entity class/property names: standard TypeScript `PascalCase`/`camelCase`,
  mapped to `snake_case` columns via explicit `name:` on each `@Column`

## Money / Decimal Strategy

Not yet applicable — no monetary fields exist in the current schema. When
introduced, monetary fields must use `DECIMAL`, never `FLOAT`/`DOUBLE`, per
`‌ai/Phase 03.md` §24-26.

## Migration Strategy

`synchronize: false` always. All schema changes go through TypeORM migrations
in `src/database/migrations/`, tracked in the `migrations` table.

```bash
npm run migration:generate -- src/database/migrations/<Name>   # generate from entity diff
npm run migration:create -- src/database/migrations/<Name>     # empty migration
npm run migration:run                                          # apply pending migrations
npm run migration:revert                                       # revert the last migration
```

The CLI DataSource (`src/database/data-source.ts`) loads `.env` directly via
`dotenv` since it runs outside Nest's dependency injection. The application
DataSource (`src/database/database.module.ts`) is built from the same
`buildDataSourceOptions()` factory (`src/database/typeorm.options.ts`) so both
paths stay consistent.

## Connection Configuration

Environment variables (validated at startup, see `src/config/env.validation.ts`):

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `DB_HOST` | No | `localhost` | MySQL host (`mysql` inside Docker) |
| `DB_PORT` | No | `3306` | MySQL port |
| `DB_USERNAME` | **Yes** | — | Application DB user (not root) |
| `DB_PASSWORD` | **Yes** | — | Application DB password |
| `DB_DATABASE` | **Yes** | — | Database name |
| `DB_POOL_SIZE` | No | `10` | Connection pool size |
| `DB_LOGGING` | No | `false` | Enable TypeORM query logging (dev only) |

## Multi-Company / RBAC / Data Visibility Preparation

No entities requiring company/branch/warehouse/role/permission scope exist
yet. `BaseEntity` deliberately contains no such fields — those are added
per-entity by the phases that own them (Phase 06 RBAC, Phase 07
Organization), so the foundation does not need to be redesigned when they
arrive.

## Transaction Strategy

TypeORM's standard transaction APIs (`DataSource.transaction()` /
`QueryRunner`) are available and will be wrapped by a reusable
`TransactionService` in Phase 04. No transactional business operations exist
yet in this phase.
